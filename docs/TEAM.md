# TalmudFinance プロジェクトチーム

> 1人開発を「6つの帽子（ロール）」を切り替えて運用する設計。
> Claude（AI）を各ロールの常設アシスタントとして使う前提。

---

## 1. プロジェクトの基本情報

| 項目 | 内容 |
|------|------|
| プロジェクト名 | TalmudFinance（タルムードに学ぶ ― 賢者の金融市場） |
| プラットフォーム | Android（min SDK 24 / target SDK 34） |
| 体制 | 1人開発（ロール切り替え型）+ Claude |
| 現フェーズ | Phase 2 開始（MVP実装完了 → コンテンツ拡充・QA・リリース準備・機能拡張） |
| 開発期間目安 | Phase 2: 約8〜12週間 |

---

## 2. ロール設計（6つの帽子）

1人開発でも責務を分けて考えることで、判断の質と作業の段取りが上がる。
1日の中で帽子を切り替える例: 朝=PM帽子で計画 → 午前=Engineer帽子で実装 → 午後=QA帽子で検証 → 夜=Content帽子で教えの監修。

### 2.1 ロール一覧

| # | ロール名 | 帽子 | 主な責務 | Claude の役立て方 |
|---|---------|------|---------|------------------|
| R1 | プロダクトマネージャー (PM) | 計画 | 優先順位、要件定義、ロードマップ管理、ユーザー価値の検証 | スプリント計画、優先順位ディスカッション、PRD ドラフト |
| R2 | エンジニア | 実装 | Kotlin/Compose 実装、テスト、ビルド、リファクタリング | コードレビュー、エラー解析、設計相談、ペアプロ |
| R3 | デザイナー | 表現 | UI/UX、配色、タイポ、アイコン、ストアスクリーンショット | ワイヤーフレーム提案、配色案、Compose の見た目調整 |
| R4 | コンテンツキュレーター | 監修 | タルムードの教えの選定・出典確認・金融視点の解釈執筆 | 教えの英日対照、解釈ドラフト、出典の検索 |
| R5 | QA / オブザーバー | 検証 | テスト計画、手動・自動テスト、クラッシュ監視、ベータ受け入れ | テストケース生成、再現手順整理、バグレポート要約 |
| R6 | リリース・マーケ担当 | 露出 | Google Play 申請、スクリーンショット、説明文、ASO、初期PR | ストア説明文、プレスリリース、ブログ案、SNS文案 |

### 2.2 「今日はどの帽子か」フロー

```
朝の15分:   PM帽子 → 今日のタスクを1〜3個決める
午前ブロック: Engineer または Content 帽子 → 集中作業
昼:         QA帽子 → 午前の成果を実機で確認
午後ブロック: Designer または Marketing 帽子 → 浅く広く
夜の15分:    PM帽子 → 進捗をBACKLOG.mdに反映
```

ポイント: **1日に切り替える帽子は最大3つ**。それ以上はコンテキストスイッチで疲弊する。

## 3. 責任マトリクス（RACI 簡易版）

R = Responsible（実作業）/ A = Accountable（最終責任）/ C = Consulted（相談） / I = Informed（共有）

| 領域 | PM | Engineer | Designer | Content | QA | Marketing | Claude |
|------|----|---------|----------|---------|----|----------|--------|
| 機能要件の決定 | A/R | C | C | I | I | I | C |
| Kotlin/Compose 実装 | I | A/R | C | I | I | I | C |
| UI/配色/アイコン | C | C | A/R | I | I | C | C |
| 教えの追加・監修 | C | I | I | A/R | I | I | C |
| バグ修正 | I | A/R | I | I | C | I | C |
| テスト計画・実行 | I | C | I | I | A/R | I | C |
| Google Play 申請 | C | C | C | I | C | A/R | C |
| ストア説明文・ASO | C | I | C | C | I | A/R | C |
| ロードマップ更新 | A/R | C | I | C | I | C | C |

## 4. コミュニケーション設計

1人開発なので「自分との対話の儀式」をテンプレ化する。

### 4.1 デイリー（5分）
- **対象ファイル**: `docs/BACKLOG.md`
- **やること**: 昨日完了の項目を ✅ にし、今日のWIPを `In Progress` に動かす

### 4.2 ウィークリー（30分・金曜夜推奨）
- **対象ファイル**: `docs/ROADMAP.md` と `docs/KPI.md`
- **やること**:
  1. 今週やったことの振り返り（KEEP / PROBLEM / TRY）
  2. KPIの実績を1行追記
  3. 来週のスプリントを3〜5項目で確定

### 4.3 マンスリー（60分）
- **対象ファイル**: ROADMAP.md の Phase 進捗
- **やること**: フェーズゲート判定（次フェーズに進めるか）

## 7. 1人開発の心得（プロジェクト固有）

タルムードの教えと整合する開発スタイル:

- **「賢者は答えるのを急がず」（教え #12）** — 新機能を即実装せず、1日寝かせる
- **「目で見ぬものに心は痛まない」（教え #18）** — 1日に複数回ストアレビューを見ない
- **「学びを毎日少しずつ積み重ねよ」（教え #20）** — 1日30分でも前進すれば良し
- **「急いで得た富は減る」（教え #6）** — 機能の詰め込みではなくMVP原則を守る
